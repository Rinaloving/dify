# 2026-06-01 Daily Notes

## SqlSugar ContainsKey 报错修复
- **问题**：`Dictionary.ContainsKey(it.Id)` 无法被 SqlSugar 翻译成 SQL
- **错误**：`The LINQ expression 'Dictionary.ContainsKey(it.Id)' could not be translated`
- **修复**：改用 `List<string>.Contains()`，SqlSugar 会翻译成 SQL `IN` 子句
- **模式**：
  ```csharp
  // ❌ 不能用
  var datasetRoleMap = ...; // Dictionary
  .Where(it => !datasetRoleMap.ContainsKey(it.Id) || ...)
  
  // ✅ 改用
  var allRestrictedDatasetIds = ...; // List<string>
  var allowedDatasetIds = ...;       // List<string>
  .Where(it => !allRestrictedDatasetIds.Contains(it.Id) || allowedDatasetIds.Contains(it.Id))
  ```

## Weaviate Class 名称 `_Node` 后缀
- **现象**：Weaviate 中的 Class 有 `_Node` 后缀（`C_xxx_Node`），但代码生成 `C_xxx`
- **验证**：Weaviate 不会自动加后缀，是之前系统（Dify）创建的
- **修复**：`AiDocumentProcessService.GenerateClassName()` 加 `_Node` 后缀
- **RagChatStream 也要改**：`LlmClientService.cs` 里两处直接用 `$"C_{...}"` 的地方也要加
- **注意**：`LlmClientService.cs` 里有两处 className 生成（非流式和流式各一处），都要改
- 影响所有检索和切片操作

## WeaviateChunk 批量删除
- **需求**：切片管理页面添加批量删除功能
- **后端**：新增 `POST /api/rb/WeaviateChunk/BatchDelete`，参数 `{ className, ids: [...] }`
- **前端**：新增 checkbox 多选 + 批量删除按钮 + 单条删除按钮
- **DTO**：新建 `WeaviateBatchDeleteInput.cs`（className + ids）
- **参考**：`xrWorkLogReview/index.vue` 的批量删除模式

## Weaviate 自动创建 Class 测试
- 用 curl 插入不存在的 Class 时，Weaviate 会自动创建 Class（不加 `_Node` 后缀）
- 这说明 `_Node` 后缀确实是之前系统显式加的，不是 Weaviate 的行为

## 今日关键发现
- SqlSugar 不支持在 LINQ 表达式中使用 C# 集合方法（`ContainsKey` 等），只能用 `Contains`（翻译成 SQL IN）
- JNPF DTO 属性必须用小写（`className` 不是 `ClassName`），因为 `PropertyNamingPolicy = null`
- Weaviate 切片管理需要完整的 CRUD，不能只读
- Weaviate 批量插入时 properties 不能有 Schema 外的字段（Id/CreatedAt/UpdatedAt），否则静默返回 FAILED
- C# float.ToString() 在中文环境下用逗号做小数分隔符，跨系统序列化必须用 CultureInfo.InvariantCulture
- Weaviate GraphQL 不支持 inline fragment 语法 `... on ClassName { fields }`
- JsonElement 反序列化时直接用 .Deserialize<T>()，不要手动转 Dictionary 丢失类型信息
- 永远不要写空的 catch 块，至少记录日志

## RAG 开发关键经验（Weaviate）
1. **向量位置**：vectorizer=none 时，向量必须在对象顶层 `{class, properties, vector}`，不能放 properties 里
2. **基类属性**：WeaviateObject 的 Id/CreatedAt/UpdatedAt 不在 Schema 中，插入前必须移除
3. **浮点序列化**：`string.Join(",", vector)` 在中文环境下会生成逗号小数，必须用 InvariantCulture
4. **GraphQL 字段名**：Weaviate 属性名大小写敏感，不要用 ToSnakeCase 转换
5. **inline fragment**：Weaviate GraphQL 不支持 `... on ClassName`，直接写字段名
6. **HTTP 200 ≠ 成功**：Weaviate 批量插入即使字段不合法也返回 200，要检查返回体的 status
7. **Class 命名**：现有数据有 `_Node` 后缀，新代码必须兼容

## 开发习惯
- **不要自动提交 Gitee** — 改完代码让用户自己验证，确认没问题后用户自己提交

## aiDocument 分页问题（21:00 进行中）
- **现象**：API 返回 `{List: [...], Total: 0, CurrentPage: 1, PageSize: 20}`（PascalCase），BasicTable 期望 `{pagination: {total: N}, list: [...]}`
- **对比**：xrHistoryToday 的 API 返回正确的 `{pagination: {total: 7}, list: [...]}` 格式
- **原因分析**：两者都用 `ToPagedListAsync()` + `PageResult<T>.SqlSugarPageResult(data)`，但 aiDocument 的 ThenMapperAsync 可能影响了返回对象
- **PageResult.SqlSugarPageResult** 方法应该把 `SqlSugarPagedList<T>` 转成 `{pagination, list}` 格式
- **怀疑**：`ThenMapperAsync` 后 data 对象可能不再是原始的 `SqlSugarPagedList` 类型，导致 `SqlSugarPageResult` 未能正确包装
- **待修复**：需要进一步调试确认 ThenMapperAsync 是否改变了返回类型

## WeaviateChunk 分页 Total:0 修复（21:15）
- **问题**：WeaviateChunk 列表 API 返回 20 条数据但 `Total: 0`
- **根因**：`WeaviateClient.ExecuteAggregateCountAsync()` 在无过滤条件时生成了无效 GraphQL：
  ```
  Aggregate { C_xxx_Node( ) { meta { count } } }  // 空括号语法错误
  ```
  catch 块静默返回 0，所以一直显示总数 0
- **额外问题**：`whereClause` 末尾有逗号（`,`），Aggregate 查询后面没有其他参数时逗号也是语法错误
- **修复**：
  - `whereClause` 为空 → 不加括号：`C_xxx_Node { meta { count } }`
  - `whereClause` 非空 → `TrimEnd(',')` 去掉尾部逗号再加括号：`C_xxx_Node(where: ...) { ... }`
- **验证**：修复后 Aggregate 查询正确返回 `count: 350`

## `.doc` 文档乱码修复（21:15-21:40）
- **问题**：`.doc`（旧 Word 格式）文件切片后中文全是乱码，`.md` 文件正常
- **根因**：`.doc` 是 OLE2 二进制格式（不是纯文本），原代码用 `StreamReader` 当纯文本读
- **NPOI HWPF 不可用**：
  - NPOI 2.5.5（MiniExcel 传递依赖）不含 HWPF 模块
  - NPOI 2.7.2（.NET Core 版本）也不含 HWPF
  - HWPF 只在 .NET Framework 版本的 NPOI 中存在
- **最终方案**：用 `OpenMcdf` 库手动解析 OLE2 二进制格式
  - 安装 `OpenMcdf` 3.1.4 NuGet 包
  - **OpenMcdf 3.x API 变化**：`CompoundFile` → `RootStorage`，`GetStream` → `OpenStream`
  - 读取 `WordDocument` 流 → 解析 FIB（File Information Block）→ 找到 CLX → 解析 PlcPcd → 提取文本
  - 支持 ANSI 和 Unicode 两种编码的 .doc 文件
  - FIB 结构：`0x0018`=复杂部分开始位置，`0x004A`=字符数，`0x004C`=ANSI字符数，`0x0050`=Flags(含 Unicode 标志)，`0x00A2`=CLX 偏移，`0x00A4`=CLX 大小
  - CLX 格式：`0x01`(Grpprl) 或 `0x02`(PlcPcd) 类型标记 + 4字节大小 + 数据，循环读取找 `0x02` 类型
  - PlcPcd 结构：数组 of CP (4字节 each, n+1个) + 数组 of PCD (8字节 each, n个)
  - PCD 结构：2字节属性 + 4字节文件位置(bit 0-29是 FC, bit 30=fCompressed)
  - Unicode 判断：`bit 0x02000000` of FIB flags，置位=Unicode(UTF-16LE)，否则=ANSI(系统默认编码)
- **需要清理**：旧的乱码切片数据需要删除后重新处理该 .doc 文档
